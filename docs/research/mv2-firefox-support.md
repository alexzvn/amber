# What it would take to add Manifest V2 / Firefox support to the amber toolchain

## Bottom line

The cheapest and most durable path is **Firefox Manifest V3 (event-page) support, not true MV2**: Firefox fully supports MV3 (generally available since Firefox 109, [Extension Workshop](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/)) and has explicitly promised no MV2 deprecation for the foreseeable future, while Chrome has already killed MV2 ([Chrome timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline)). Amber's runtime is unexpectedly close to working on Firefox MV3 as-is because Firefox returns Promises from the `chrome.*` namespace in MV3 since Firefox 106 ([bug 1711570](https://bugzilla.mozilla.org/show_bug.cgi?id=1711570)), and amber's message handler already uses the maximally portable `return true` pattern. The real work is in the bundler: emit `background.scripts` event pages alongside the service worker (a manifest that works on Chrome 121+/Firefox 121+), add `browser_specific_settings.gecko.id`, replace the Puppeteer/Chromium dev-browser launch with `web-ext run`, and rework the service-worker-only dev HMR and `getMode()` runtime detection for Firefox's document-based background.

## Scope & method

This note is a research artifact, not a design doc. Every external claim is anchored to a primary source: MDN WebExtensions reference pages and their browser-compat data (mdn/browser-compat-data JSON), `extensionworkshop.com`, Mozilla Add-ons blog and Bugzilla, `developer.chrome.com` extension docs, the W3C WebExtensions Community Group work referenced by those pages, and the actual source of `mozilla/webextension-polyfill` and `wxt-dev/wxt` (read from fresh shallow clones at commit of this writing). Claims about this repo cite `packages/*/src/**` files with line numbers read directly. Where a fact could not be verified from a primary source it is marked `[INFERENCE]` or listed in [Open questions](#open-questions). No source code was modified; the only file written is this one.

## Findings

### (a) Is MV2 still accepted by AMO, and for how long?

- Firefox has **no MV2 deprecation plan**: "Firefox ... has no plans to deprecate MV2 and will continue to support MV2 extensions for the foreseeable future. And even if we re-evaluate this decision at some point down the road, we anticipate providing a notice of at least 12 months" — [Mozilla Add-ons blog, March 13 2024](https://blog.mozilla.org/addons/2024/03/13/manifest-v3-manifest-v2-march-2024-update/). This is the most recent explicit statement; the June 2025 Add-ons policy update ([Discourse announcement](https://discourse.mozilla.org/t/add-ons-policies-changes-june-2025/144331)) made no MV2 acceptance changes.
- AMO distributes both manifest versions today; the official dual-distribution flow ("list MV2 on AMO, sign an MV3 build for self-distribution") is documented at [Extension Workshop, "Distribute Manifest V2 and V3 extensions"](https://extensionworkshop.com/documentation/publish/distribute-manifest-versions/).
- Contrast — Chrome: MV2 extensions were disabled for all users in Chrome 138 (July 24 2025) and all remaining MV2 extensions are removed from the Chrome Web Store on August 31 2026 ([Chrome Manifest V2 support timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline)). So an MV2 output would be Firefox-only.
- `[INFERENCE]` Because the only MV2-capable browsers left are Firefox (and forks), an MV2 target has a small and shrinking audience: every currently supported Firefox release channel (and ESR 128+) supports MV3.

### (b) Firefox MV3 vs Chrome MV3 — what differs

- **Background:** Firefox does **not** support `background.service_worker` ([Firefox bug 1573659](https://bugzil.la/1573659)); it runs MV3 backgrounds as non-persistent event pages via `background.scripts`/`background.page` ([MDN background](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#browser_support)). Since Firefox 121 the background page starts even when `service_worker` is also present (bug [1860304](https://bugzil.la/1860304)); Chrome 121+ ignores `background.scripts` in MV3. MDN therefore recommends a single cross-browser MV3 manifest specifying **both** keys ([MDN background, "Cross-browser Manifest V3 background scripts"](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#cross-browser_manifest_v3_background_scripts)).
- **Host permissions:** Firefox MV3 (≤126) did not grant `host_permissions` at install; from Firefox 127 they are shown in the install prompt and granted, and users can grant/revoke them at any time ([Extension Workshop MV3 migration guide](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/)). Extensions must tolerate missing host permissions at runtime.
- **webRequest:** Firefox keeps blocking `webRequest` in MV3, a deliberate divergence from Chrome ([Mozilla blog, March 2024](https://blog.mozilla.org/addons/2024/03/13/manifest-v3-manifest-v2-march-2024-update/)).
- **CSP:** MV3 `content_security_policy.extension_pages` permits only `'self'`, `'none'`, `'wasm-unsafe-eval'` in script directives, plus an `upgrade-insecure-requests` default; inline scripts are forbidden ([MDN content_security_policy](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_security_policy)). Same shape as Chrome; no extra divergence for amber's purposes. Dev-only relaxation: scripts from localhost may be allowlisted "for unpacked extensions from Chrome 110 and temporarily loaded extensions from Firefox 147" ([MDN CSP, "Scripts from localhost"](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_security_policy)).
- **userScripts:** Firefox's MV3 `userScripts` API is incompatible with the MV2 `userScripts` (legacy) API; both exist ([June 2025 policy thread, Simeon Vincent](https://discourse.mozilla.org/t/add-ons-policies-changes-june-2025/144331)). Not relevant to amber's runtime.
- **Chrome-only APIs:** Chromium-only capabilities such as `offscreen` documents have no MDN/BCD entry ([INFERENCE] from absence of MDN data; Chrome docs for [offscreen](https://developer.chrome.com/docs/extensions/reference/api/offscreen) exist, Firefox documents no equivalent). Nothing in amber's runtime or bundler uses them today.

### (c) `browser.*` vs `chrome.*` namespace and promise-vs-callback semantics

- Firefox and Safari expose the APIs under `browser` (promises); Firefox *also* supports `chrome` "using callbacks and `browser` using promises" as a porting aid ([MDN Chrome incompatibilities](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Chrome_incompatibilities)).
- **In MV3, Firefox additionally returns Promises from `chrome.*`**: bug [1711570](https://bugzilla.mozilla.org/show_bug.cgi?id=1711570) ("support promises on chrome namespace", firefox106 fixed, whiteboard `mv3:m3`; attachment "allow promises with chrome namespace in mv3"). Confirmed by the [MV3 migration guide](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/): "In Manifest V2, Firefox extensions support the use of the `chrome.*` namespace with APIs that provide asynchronous event handling using callbacks. In Manifest V3, Firefox supports promises for asynchronous events in the `chrome.*` namespace."
- In content scripts `chrome === browser` in Firefox ([bug 1711570 comment 1](https://bugzilla.mozilla.org/show_bug.cgi?id=1711570#c1)).
- Chrome: `chrome.*` only, with Promises on most MV3 methods and callbacks for backward compatibility ([MDN Chrome incompatibilities](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Chrome_incompatibilities)). Chrome added a parallel `browser` namespace in Chrome 148 ([Chrome, "Transition to browser namespace"](https://developer.chrome.com/docs/extensions/develop/concepts/browser-namespace)).
- Consequence for amber: the runtime's `await chrome.runtime.*` code (see [coupling table](#current-mv3-coupling-in-amber)) works unchanged in Firefox **MV3** but breaks under Firefox **MV2**, where `chrome.*` is callback-only.

### (d) `browser_specific_settings.gecko` requirements

- `gecko.id` is **mandatory for signing MV3 extensions** ("AMO does not assign an ID"); for MV2 it is optional but recommended, with AMO assigning a GUID if absent ([MDN browser_specific_settings](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings#id)). `web-ext sign` likewise requires it for MV3 ([Extension Workshop, web-ext getting started](https://extensionworkshop.com/documentation/develop/getting-started-with-web-ext/)).
- `strict_min_version`: minimum Gecko version; `"*"` is invalid; note that Firefox versions below 115.0 ESR / 128.0 no longer recognize extension signatures due to the March 2025 root-certificate expiry ([MDN browser_specific_settings](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings#strict_min_version)).
- From November 3 2025, new AMO submissions must also declare `gecko.data_collection_permissions` ([MDN browser_specific_settings](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings#data_collection_permissions)).
- Chrome ignores `browser_specific_settings` entirely ([MDN browser_specific_settings](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/browser_specific_settings#chrome_properties)), so it can be emitted unconditionally.

### (e) ES-module content scripts

- No browser exposes a manifest-level ES-module option on `content_scripts`: the `content_scripts` key's documented properties (including `world`, added Firefox 128) contain no `type` field ([MDN content_scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_scripts); BCD `webextensions/manifest/content_scripts.json` has no `type` entry). This is exactly why the MV3 ecosystem (including amber) bundles content scripts as classic scripts / IIFE loaders.
- Firefox: dynamic `import()` in content scripts works since Firefox 89 ([bug 1536094](https://bugzilla.mozilla.org/show_bug.cgi?id=1536094), fixed firefox89; documented at [MDN Content scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts#loading_content_scripts)). Static ES-module content scripts remain unimplemented ([bug 1451545](https://bugzilla.mozilla.org/show_bug.cgi?id=1451545), "Support loading content scripts as ES6 modules", NEW).
- **Live risk:** dynamic `import()` in **MV3** Firefox content scripts is reported broken — "Module source URI is not allowed in this document" — in [bug 1803950](https://bugzilla.mozilla.org/show_bug.cgi?id=1803950) (P2, NEW, last updated August 2025). Amber's content-script loaders are dynamic-import based (`packages/bundler/src/client/content-script.iife.prod.js` is `(async () => await import(__SCRIPT__))()`), so this must be validated on current Firefox before shipping a Firefox target.

### (f) Does Firefox need the inline-script / CSP polyfills at all?

- **InlineScriptPolyfill — yes, for Firefox MV3 pages.** MV3 CSP forbids inline scripts in Firefox exactly as in Chrome (only `'self'`/`'none'`/`'wasm-unsafe-eval'` in `script-src`, [MDN content_security_policy](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_security_policy)). Under MV2 the CSP may be relaxed with script hashes, so the polyfill would be unnecessary-but-harmless there ([MDN content_security_policy, MV2 relaxation](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_security_policy#manifest_v2_syntax)).
- **ContentModulePolyfill — yes.** Firefox offers no static ES-module content scripts (finding (e)), so the IIFE-loader workaround is still required.
- **bypassCSP / DNR header rewrite — needed for Firefox dev, but only below Firefox 147.** Firefox 147+ permits `http://localhost` in the `extension_pages` CSP for temporarily loaded extensions ([MDN CSP, "Scripts from localhost"](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_security_policy)), which is a cleaner dev-time alternative to rewriting CSP headers. For Firefox < 147, the DNR-based bypass (finding (g)) is the available mechanism.

### (g) `declarativeNetRequest` in Firefox: availability and limits

- Available since Firefox 113, including `updateDynamicRules` and the `modifyHeaders` action with `responseHeaders`/`requestHeaders` (BCD `webextensions/api/declarativeNetRequest.json`; summary at [MDN declarativeNetRequest](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/declarativeNetRequest)).
- Limits: dynamic+session rules shared limit until Firefox 127; from Firefox 128 the limits split into `MAX_NUMBER_OF_DYNAMIC_RULES` and `MAX_NUMBER_OF_SESSION_RULES` ([MDN declarativeNetRequest, "Dynamic and session-scoped rules"](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/declarativeNetRequest#dynamic_and_session-scoped_rules)).
- Unsupported in Firefox: `getMatchedRules`, `onRuleMatchedDebug` (feedback requires the `extensions.dnr.feedback` pref, [MDN declarativeNetRequest, Testing](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/declarativeNetRequest#testing)), and response-header *matching* conditions (`RuleCondition.responseHeaders`, BCD `False`). None of these are used by amber.
- Header modification requires **host permissions** for the request URL (and, for non-navigation requests, the initiator); navigation requests (`main_frame`/`sub_frame`) need only the request URL ([MDN declarativeNetRequest, Permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/declarativeNetRequest#permissions)). Amber's bypass rule is `MAIN_FRAME`/`SUB_FRAME`-only and its dev flow already adds the bypass hosts to `host_permissions`, which satisfies this in both browsers.
- `[INFERENCE]` MDN does not state a manifest-version gate on DNR in Firefox, so the same bypass client should work on Firefox MV2; this is untested and flagged in [Open questions](#open-questions).

### (h) `chrome.storage.session` in Firefox

- `storage.session` is supported since Firefox 115 (BCD `webextensions/api/storage.json`: `storage/session -> firefox: 115`); 10 MB quota; `QUOTA_BYTES` property since 131; **`setAccessLevel` is not supported** in Firefox (BCD `False`). All operations amber's `Storage` wrapper uses (`get`, `set`, `remove`, `getBytesInUse`, `onChanged`) are available, so `Storage.session` works on Firefox ≥ 115 as long as `setAccessLevel` is not called.

### (i) `sendMessage`/`onMessage` async-response semantics — the `return true` vs Promise divergence

- Firefox: an `onMessage` listener may return a Promise (preferred) *or* return `true` and call `sendResponse` later ([MDN runtime.onMessage](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessage)).
- Chrome: until Chrome 148, Promise-returning listeners were unsupported (crbug 1185241); from Chrome 148 they are supported but "rolling out gradually", and `return true` "will continue to work" regardless ([Chrome, Message passing](https://developer.chrome.com/docs/extensions/develop/concepts/messaging); [Chrome, Transition to browser namespace](https://developer.chrome.com/docs/extensions/develop/concepts/browser-namespace)).
- Amber's `MessageHandler.ts` already uses the **portable pattern**: `chrome.runtime.onMessage.addListener(...); ... return true` with a later `response(...)` call (`packages/amber/src/messaging/MessageHandler.ts:33-55`, `:66-84`). This works on every Chrome and Firefox version in both manifest versions; **no change needed**.

### (j) `web_accessible_resources` shape

- MV2: plain array of path strings. MV3: array of objects `{ resources, matches | extension_ids, use_dynamic_url? }` ([MDN web_accessible_resources](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/web_accessible_resources)). Firefox MV3 supports `extension_ids`, `matches`, `resources` but **not `use_dynamic_url`** ([Extension Workshop MV3 migration guide](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/)).
- Amber emits the MV3 object form everywhere (see table); an MV2 target must flatten it to the string-array form, exactly as wxt's `convertWebAccessibleResourcesToMv2` does ([wxt source](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/core/utils/manifest.ts)).

### (k) How Firefox extensions are loaded for development

- `web-ext run` launches Firefox, loads the extension temporarily "just as you can on the about:debugging page", watches files and auto-reloads (or press `r`); options include `--firefox` (binary path), `--firefox-profile`, and `web-ext run --target=firefox-android` ([Extension Workshop, Getting started with web-ext](https://extensionworkshop.com/documentation/develop/getting-started-with-web-ext/)). Temporary loading via RDP has the same limitations as `about:debugging` for permission prompts and restart features.
- Manual path: `about:debugging` → This Firefox → Load Temporary Add-on → Inspect (Toolbox) for background/popup/options debugging ([Extension Workshop, Debugging](https://extensionworkshop.com/documentation/develop/debugging/)). The Toolbox itself is served over the Remote Debugging Protocol; a Debug Adapter for Firefox implements DAP for IDE integration ([Extension Workshop, Debugging](https://extensionworkshop.com/documentation/develop/debugging/)).
- Amber's current dev browser is `playwright-extra` Chromium launched with `--load-extension=<dist>` (`packages/bundler/src/cli/dev/browser.ts:19-27`); that flag and profile-model are Chromium-only, so the Firefox dev driver must be a different implementation. wxt solved this with a runner abstraction whose Firefox implementation wraps `web-ext` (`webExt.cmd.run`) ([wxt source, runners/web-ext.ts](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/core/runners/web-ext.ts)).

### Toolchain reality check: how wxt branches on manifest version and browser

- wxt has a first-class `manifestVersion` config option (`2 | 3`) plus `--mv2`/`--mv3` CLI flags, and **ignores** `manifest.manifest_version` in user config with a warning ([wxt source, core/utils/manifest.ts:68-82](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/core/utils/manifest.ts)).
- On MV2 it runs manifest conversions: `convertWebAccessibleResourcesToMv2` (flatten objects to strings), `convertActionToMv2` (`action` → `browser_action`), `convertCspToMv2` (object → string), `moveHostPermissionsToPermissions` ([wxt source, manifest.ts:154-159, 656-716](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/core/utils/manifest.ts)).
- Background emission branches three ways ([wxt source, manifest.ts:234-255](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/core/utils/manifest.ts)): Firefox+MV3 → `{ type, scripts: [...] }` (event page); other MV3 → `{ type, service_worker }`; MV2 → `{ persistent, scripts: [...] }`.
- Firefox runner: `createWebExtRunner()` wraps `web-ext` ([wxt source, runners/web-ext.ts](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/core/runners/web-ext.ts)); Firefox MV3 also triggers a warning when the extension ID is missing ([wxt source, manifest.ts:137-141](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/core/utils/manifest.ts)).

## Options

### Option 1 — Firefox MV3 (event pages) only

Keep `manifest_version: 3` for both browsers. Emit the cross-browser background (`service_worker` + `scripts`) per MDN's recommendation so one build loads in Chrome 121+/Firefox 121+ ([MDN background](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#cross-browser_manifest_v3_background_scripts)), or emit `background.scripts` when the target is Firefox. Add `browser_specific_settings.gecko` (id + `strict_min_version`), swap the dev browser for `web-ext`, fix `getMode()` and the HMR client for event pages, and validate the content-script loaders against [bug 1803950](https://bugzilla.mozilla.org/show_bug.cgi?id=1803950). Runtime changes are near zero because `chrome.*` Promises exist on Firefox MV3 (finding (c)).

Tradeoffs: small, focused surface; no second manifest; reaches every supported Firefox (ESR 128+, FF 109+); Mozilla's own direction is MV3. Costs: dev-HMR rework for the document background; DNR-based CSP bypass needed for Firefox < 147.

### Option 2 — True MV2 (Firefox-only)

Add a `manifest_version: 2` output (Chrome MV2 is dead, finding (a)): `background.scripts` + `persistent`, `browser_action` instead of `action`, `host_permissions` folded into `permissions`, string-array `web_accessible_resources`, string CSP — the exact conversions wxt implements ([wxt manifest.ts:154-159, 656-716](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/core/utils/manifest.ts)). The runtime must stop awaiting `chrome.*` (callback-only in Firefox MV2, finding (c)): either switch to `browser.*` where available or ship a small promisify shim.

Tradeoffs: maximizes reach on old Firefox only; buys nothing for the future since Firefox keeps adding MV3 features and every supported Firefox already speaks MV3; requires a runtime namespace/shim layer that Option 1 avoids entirely; AMO could still sunset MV2 someday (12-month notice promised, finding (a)).

### Option 3 — Dual-target (MV2 + MV3 outputs)

wxt-style `manifestVersion` config with conversions for MV2 and the existing MV3 path kept intact (wxt ships both simultaneously; [wxt manifest.ts](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/core/utils/manifest.ts)). Highest cost: two manifest emitters, two background shapes, runtime namespace shim for MV2, two dev runners. Value: a single source tree serving legacy Firefox; realistically only worth it if a concrete MV2-only consumer (old ESR deployments, Firefox forks) is on the roadmap.

## Recommendation

**Pursue Option 1: Firefox Manifest V3 (event-page) support, and treat true MV2 as out of scope for now.**

Reasoning: (1) It is the smallest correct step — the runtime's promise-based `chrome.*` code already runs on Firefox MV3 (finding (c)), the message handler's `return true` pattern is already portable (finding (i)), and `storage.session`, DNR, and the MV3 WAR/CSP shapes all exist in Firefox (findings (g), (h), (j)). (2) It matches where the industry is: Chrome has removed MV2 entirely (finding (a)), and Firefox's MV2 commitment is explicitly "for the foreseeable future" with MV3 as the platform it keeps investing in (findings (a), (b)). (3) The bundler work is contained: a target/browser-aware manifest writer (background dual-key or Firefox `scripts`, `browser_specific_settings.gecko`, MV2-only conversions deferred), an event-page-safe dev HMR, and a `web-ext` dev runner — all patterns already proven in wxt's source. Do not adopt `webextension-polyfill`: it is the reverse direction (it polyfills `browser.*` for Chrome, not `chrome.*` for Firefox), is a no-op on both Firefox and Chrome 148+, and its maintainers have frozen it ([README](https://github.com/mozilla/webextension-polyfill)); a small internal namespace resolver is all the runtime would ever need, and only for MV2.

## Open questions

- Firefox dynamic `import()` in **MV3** content scripts: [bug 1803950](https://bugzilla.mozilla.org/show_bug.cgi?id=1803950) (P2, NEW, Aug 2025) reports "Module source URI is not allowed in this document" — must be smoke-tested on current Firefox/Nightly before relying on amber's IIFE loaders for Firefox. Related: does listing the module under `web_accessible_resources` (which amber's `ManifestWriter` already does, `packages/bundler/src/plugins/ManifestWriter.ts:10-27`) work around it?
- Does `declarativeNetRequest` function in Firefox **MV2** extensions (MDN documents the API but not a manifest-version gate; finding (g))? If not, Option 2's dev loop needs a different CSP bypass for Firefox < 147.
- `getMode()` fix (`packages/amber/src/messaging/MessageMisc.ts:47-50`): what is the most reliable Firefox MV3 background detection — the `background` marker is currently inferred from "no `window`", which fails for event pages; `[INFERENCE]` that `chrome.runtime.getBackgroundPage()` availability or an injected build-time constant is the fix, but this needs a decision.
- Whether the dual-key background manifest (`service_worker` + `scripts`, [MDN](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background#cross-browser_manifest_v3_background_scripts)) interacts safely with amber's dev-time worker injection (`ManifestWriter.ts:37-46`) on Firefox — the injected `worker.esm` is service-worker-only and would be a no-op/broken entry in a Firefox event page.
- Exact `web-ext` version to pin for the dev runner and whether `web-ext run`'s reload replaces amber's WebSocket HMR on Firefox entirely, or whether an event-page HMR client (port-based, using `runtime.connect`) is worth building to preserve hot-update UX parity.
- Firefox MV3 host-permission semantics (finding (b)): amber's dev flow pushes `http://localhost:<port>/*` into `host_permissions` (`ManifestWriter.ts:63-74`); with Firefox's user-revocable host permissions, dev servers may silently lose permission mid-session — needs UX handling.
